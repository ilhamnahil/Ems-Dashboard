# 🚑 EMS Response-Time Analytics Dashboard

**How fast does an ambulance arrive in New York City, and when and where is it slower?**

An end-to-end analytics project on public emergency medical services (EMS) data:
an ETL pipeline pulls NYC's EMS dispatch records from the open-data API, cleans them with Pandas,
stores them in a SQL database, and an interactive Streamlit dashboard analyses response times by
borough, hour of day, weekday and incident type.

![Dashboard](docs/dashboard.png)

## What the dashboard shows

- **KPIs**: number of incidents, median and 90th-percentile response time, share of incidents reached
  within an adjustable target (e.g. 8 or 10 minutes), and the split into **dispatch time** (call → unit assigned)
  and **travel time** (unit on the way → on scene).
- **By borough**: median vs. 90th percentile, with the target as a reference line.
- **By hour of day**: call volume and median response time on one chart, which shows whether peak demand slows response.
- **Weekday × hour heatmap**: the slowest time slots at a glance.
- **Call types and distribution**: most frequent incident types and the full response-time distribution.
- **Filters**: period, boroughs, life-threatening incidents only (NYC severity 1–3) and call types.

## Data

[NYC Open Data, EMS Incident Dispatch Data](https://data.cityofnewyork.us/Public-Safety/EMS-Incident-Dispatch-Data/76xm-jjuj)
(dataset `76xm-jjuj`), published by the FDNY. Each row is one EMS incident with timestamps from call creation to hospital
arrival, the call type, the severity level and the borough.

> The screenshots above show the **synthetic demo sample** (`data/sample_synthetic.csv`), which was generated by `make_sample.py`
> in the same format so the project runs offline and in tests. With internet access, the app loads the real data.

## Pipeline

```
NYC Open Data API ──extract──▶ Pandas ──transform──▶ SQLite (ems.db) ──SQL queries──▶ Streamlit dashboard
  (paged, newest first)      clean, validate,       incidents + meta     filtering and       KPIs and Altair charts
                             derive features         tables               GROUP BY
```

| Step | What happens (`ems_pipeline.py`) |
|---|---|
| **Extract** | Pages through the Socrata API (`$select`, `$order`, `$limit`, `$offset`) with retries; optional app token for higher rate limits. |
| **Transform** | Parses timestamps and numbers; keeps only incidents NYC flags with a valid response time; drops duplicates and impossible values (> 3 h); converts seconds to minutes; derives hour, weekday, readable borough names, final call type and a *life-threatening* flag (severity 1–3). |
| **Load** | Writes an indexed `incidents` table and a `meta` table (source, load time, date range) into SQLite, using an atomic file swap so the dashboard never reads a half-written database. |
| **Analyse** | Filtering and aggregation in SQL (`GROUP BY` borough and call type); percentiles in Pandas, since SQLite has no percentile function. |

## Quick start

```bash
git clone https://github.com/ilhamnahil/ems-dashboard.git
cd ems-dashboard
pip install -r requirements.txt

python ems_pipeline.py              # download the latest 100,000 incidents into ems.db
streamlit run app.py
```

Offline? Run `python ems_pipeline.py --sample` to build the database from the synthetic sample instead.
If no database exists yet, the app downloads the data itself on first start, and falls back to the sample if the API can't be reached.

Options: `--limit 300000` for more history, `--app-token <token>` for a free
[NYC Open Data app token](https://data.cityofnewyork.us/profile/edit/developer_settings).

## Deploy for free

Push the repo to GitHub, then create an app on [share.streamlit.io](https://share.streamlit.io) with `app.py` as the main file.
On first start, the app downloads the real data. Optionally, add `NYC_APP_TOKEN = "..."` under **Settings → Secrets**.

## Tests

```bash
pip install pytest
pytest
```

The tests cover cleaning rules, derived fields, SQL filters, KPIs and API paging (with a mocked HTTP session).
